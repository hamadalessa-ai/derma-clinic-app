# CLAUDE.md — project rules

@AGENTS.md

## Product

Arabic-first SaaS for dermatology & aesthetic clinics in Saudi Arabia: booking, WhatsApp reminders,
patient records + e-consents, package/session balances, a WhatsApp AI receptionist, and a
draft-only AI scribe. Multi-tenant: many clinics, strictly separated.

**This is a DEMO. Fake patient data only. No real patient data, ever, in this phase.**

## Working rules

- The founder is non-technical: explain each step simply, show a plan before coding.
- Commit in small steps. Never continue while tests fail (`pnpm check` must pass before every commit).
- Never commit secrets. Real values live only in `.env.local` (git-ignored), Vercel and Supabase settings.
  Never ask for passwords/keys in chat.
- Do not swap any part of the stack without asking.

## Stack (fixed)

- Next.js (App Router, v16 — read `node_modules/next/dist/docs/` first) + TypeScript, pnpm
- Tailwind CSS v4 + shadcn/ui-style components (`src/components/ui`), lucide icons
- next-intl: Arabic default (RTL), English toggle (cookie `NEXT_LOCALE`, no locale in URL); font IBM Plex Sans Arabic
- PostgreSQL + Drizzle ORM (driver: `postgres`), Better Auth (self-hosted, email + password)
- Zod, React Hook Form, Vitest
- Hosting: Vercel (free) + Supabase **used only as plain Postgres** (no Supabase Auth/Storage/Realtime/SDK).
  Must stay portable to a Saudi-hosted Postgres later.

## Tenant isolation (never weaken)

- Every table except `tenants`, the auth tables (`users`, `sessions`, `accounts`, `verifications`,
  `two_factors`) and `global_rate_hits` (hashed cross-clinic rate-limit counters, no clinic data)
  has `tenant_id`, plus composite foreign keys `(tenant_id, x_id)` so rows can't point at another clinic.
- Every tenant table has RLS **ENABLED + FORCED**; policy `tenant_id = app_current_tenant()`, which reads
  `current_setting('app.tenant_id')` and is NULL (→ zero rows) when unset. Fail closed.
- The app connects as role `clinic_app` (LOGIN, NOBYPASSRLS, not table owner). Never the admin user.
- All tenant data access goes through `withTenant(tenantId, fn)` (`src/db/tenant.ts`), which uses
  a transaction-local setting — safe with Supabase's transaction pooler (port 6543, `prepare: false`).
- The clinic comes from the subdomain (`derma.localhost`); hosts outside `APP_ROOT_DOMAIN`
  (e.g. `*.vercel.app`) fall back to `DEMO_DEFAULT_CLINIC`.
- Next.js Cache Components stay OFF: no cross-request caching of clinic data.
- Security headers + Content-Security-Policy live in `next.config.ts` (only Daily may be framed; nobody may frame us).
  Signed-link pages (`/visit`, `/sign`, `/care`, `/invite`, `/instructions`) are never cached or indexed.
- Platform owners have NO backdoor to patient data.

## Roles

`platform_owner` (on `users`), and per clinic in `tenant_members`: `clinic_admin`, `practitioner`,
`receptionist`, `assistant` (nurse / doctor's assistant). Permissions live in `src/lib/auth/permissions.ts`; pages call `requirePermission()`.
`db/setup.sql` and `db/reset.sql` are both generated by `pnpm db:build-setup` (tests check they're current).
Receptionists can never see clinical notes. A member can hold several roles (`tenant_members.roles`, at least one);
any role that allows something grants it. Clinical notes need the `practitioner` role (admins alone are blocked).
A nurse / assistant works for the doctors linked in `care_team` (`src/lib/care-team/care-team.ts`, Settings → Team):
she sees their day (My Day), opens their visit screen, brings the patient in, prepares the note IN THE DOCTOR'S
NAME (`clinical_notes.entered_by_*`) and may POST the visit; she never signs a note on its own (`signNote`), never
adds addenda, never sees other doctors' notes. The
database enforces it (`app_assists()` in `db/rls.sql`).

## Phase 1 rules (never bypass)

- Booking, moving, cancelling and status changes go ONLY through `src/lib/booking/engine.ts`.
  Reservations (who/what is busy) are written by database triggers; the exclusion constraint
  `reservations_no_overlap` makes double-booking impossible. Never insert reservations by hand.
- Database calls for a signed-in user use `withActor(actorOf(ctx), …)`: Postgres then also knows
  the user, roles and allowed branches (RLS hides other branches; notes need the practitioner role).
- Package balances change only by inserting `package_session_events` (trigger + CHECK; check-in
  deduction is unique per appointment). Signed consents, files, payments and audit logs are append-only.
- The official consent record is the `patient_consents` row (text snapshot + version + fingerprint +
  signature + who/when). The print page and PDF are views of it. Files go through `getFileStore()` only.
- Screens use theme tokens (`src/app/globals.css`, `src/app/theme.ts`) and shared components only;
  `tests/theme.test.ts` fails on hard-coded colours.
  The look follows the "Clinic App Design System" (Claude artifact): brand fill only for the ONE main action,
  brand text = `text-brand-strong`, packages = `gold`, cards `rounded-xl border shadow-card`, controls `rounded-lg`,
  dialogs `rounded-2xl` (bottom sheet on phones). Success after an action = `FormSuccess` (a toast; `inline` to
  keep it on the page); errors stay inline (`FormError`). Busy buttons: `<Button loading>`. Empty lists: `EmptyState`.
- Server actions live in `src/app/actions/clinic.ts`, validate with Zod and run through `staffAction()`.
  Public pages (`/book`, `/my`) use `src/app/actions/patient.ts` + `publicAction()`: a verified mobile code
  or a patient session (`src/lib/portal/session.ts`) decides what the visitor may do; patient reads run with
  role `patient` + `app.patient_id` (RLS patient walls: own + family rows only, never notes, no writes).
- Online booking is OTP-first: step 1 mobile + code (`verifyBookingPhoneAction`) sets a signed 30-minute
  `booking_pass` cookie (`src/lib/verify/pass.ts`); confirming then needs no second code, only for THAT mobile
  (`src/lib/verify/identity.ts`; a signed-in patient counts as verified). `/book?service=<id>&mode=clinic|video`
  pre-selects from the clinic website.
- Consent links (`/sign/<appointmentId>.<sig>`, `consentToken` in `src/lib/video/link.ts`): WhatsApp messages link
  straight to the consent THIS visit needs; `signConsentByLink` records it as the patient's (no code). Only while
  the visit is open and a signature is still needed.
- Codes are shown on screen ONLY for `is_demo` clinics with `MESSAGE_DEMO_MODE=on` (`src/lib/messaging/sender.ts`).
- WhatsApp: every message goes through `src/lib/whatsapp/send.ts` (dedupe key claimed before sending →
  at most once; consent rules; demo simulator / live provider chosen by settings in `config.ts`).
  Everything patients send goes through `handleInbound()` (`inbound.ts`) — simulator and webhook alike.
  Wording lives in `catalog.ts`; after changing it run `pnpm docs:whatsapp` (a test checks the doc).
  The scheduler (`scheduler.ts`) skips already-sent keys (`SCHEDULED_KEYS` in `outbox.ts`) in one query, sends a few
  at a time and stops before its time budget (`more: true` → the hourly workflow calls again).
  Each clinic has its OWN number (`tenants.whatsapp_*`, token encrypted by `src/lib/security/secret-box.ts`),
  connected by the platform owner (Platform → clinic → WhatsApp tab; `src/lib/platform/whatsapp.ts`); one Meta app
  for all clinics (`WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, optional `WHATSAPP_ACCESS_TOKEN`); the webhook
  routes by `phone_number_id`. A demo clinic never sends real WhatsApp. The old single-clinic env setting still works.
- Business logic also checks permissions (`assertCan`), not only the screens.
- AI receptionist (`src/lib/ai/receptionist.ts`, client `src/lib/ai/claude.ts`, key `ANTHROPIC_API_KEY`):
  answers typed WhatsApp text from `handleInbound()` ONLY through its tools; it never takes a patient id
  (always the chat's own patient + family). Book / cancel / move = `propose_action`, then `confirm_action`
  only after a NEWER patient message. Never medical advice → `hand_off_to_staff`. It stays quiet when the
  clinic switched it off, no key, staff took over or replied (`conversations.ai_paused_at`), or the daily
  limit is reached. After a hand-off the chat stays "needs reply" but the AI still helps with other things
  (never the handed-off topic). Any failure → "needs reply" + a fixed reply. Tests use a scripted fake client.
  Safety net: every typed message is flagged "needs reply" when saved; the AI clears it only after its answer
  is sent (and only if the chat wasn't already waiting). One turn has a 40 s budget (`TURN_BUDGET_MS`), the client
  retries once when the API is busy, and `confirm_action` acts only when code (`isClearYes`) sees a clear "yes".
  Opening hours given to the AI come from `hours.ts` by date (holidays and day-offs included).
- AI scribe (`src/lib/ai/scribe.ts`, UI `src/components/clinic/ai-scribe.tsx`): browser dictation (Web Speech
  API; audio never reaches us) → Claude → English draft appended to the AUTHOR's own UNSIGNED note, marked
  `clinical_notes.ai_drafted_at`. Never signs, never adds diagnoses/codes/doses of its own; the spoken text is
  never stored or audited. Needs `tenant_settings.ai_scribe_enabled` + `ANTHROPIC_API_KEY`.
- Video consultations (`src/lib/video/`): services with `is_virtual` are booked in the branch's video room
  (`rooms.is_virtual`, never reserved by the trigger; the doctor still is). Patients join from a SIGNED link
  (`/visit/<appointmentId>.<sig>`, `link.ts`), doctors from My Day (`/visits/<id>/video`, own appointments only).
  Join only around the visit time and after the `telehealth` consent (`visit.ts`). The provider (Daily today,
  key `DAILY_API_KEY`) sits behind `provider.ts` so it can be swapped for a Saudi-hosted server. Never recorded.
  The patient joining = check-in (`videoCheckIn`: consent → package deduction once → "arrived").
- Doctor's visit screen `/visits/<id>` (`src/lib/visits/visit.ts`, UI `visit-workspace.tsx`): "Start visit" (arrived →
  in_session + the visit's ONE note draft + the booked service as an invoice line) and "Post visit" (`postVisit`:
  note + complete in ONE transaction, no separate signing step). Own appointments (or assisted doctors') only.
  While open, the visit gets medication / treatment orders (`visit_orders`, clinic instructions, not a Wasfaty
  prescription) and invoice codes (`visit_charges`: a service or a price-list item from `billing_items`, Setup →
  Price list; code, name and price are COPIED at that moment). Once completed / cancelled / no-show, orders and
  codes are locked by the database (`app_visit_open()`); the note by the signed-note trigger. Corrections = addenda.
  The daily invoicing file lists one row per invoice line, plus a `visit_payment` row per checkout (amount, method,
  `clinic_invoice_no` on both). Never put medication text in audit metadata.
  Video calls show on the same screen (`/visits/<id>/video` redirects there).
- Reception flow board (Calendar → "Patient flow", `src/lib/views/flow.ts`, `flow-board.tsx`): Expected → Waiting →
  With nurse → With doctor → Done, with time in each step. The times (`appointments.arrived_at`, `in_room_at`,
  `doctor_at`, `completed_at`) are written ONLY by the booking engine (`applyStatus`, `markDoctorWithPatient`);
  "with doctor" = the doctor started the visit or the nurse pressed "Ready for doctor" (`readyForDoctor`, push
  `doctor_needed`). Posting a visit pushes `ready_for_checkout` to reception. Demo refresh shifts these times too.
- Checkout (`/checkout/<id>`, `src/lib/visits/checkout.ts`, permission `visits:checkout`: admin + reception): the
  visit's invoice lines (package sessions at 0; no lines → the booked service at list price), payment, method and
  the invoice number from the clinic's OWN (ZATCA) system → ONE `visit_checkouts` row per visit, append-only, only
  for a completed visit (database policy `app_visit_completed()`). The amount due is computed on the server.
  Treatment-plan orders suggest the next sessions (first free time from each target day, same doctor first),
  booked through the normal booking engine. Patient instructions = `InstructionSheet` (orders + next
  appointments, never notes): printed at `/instructions/<id>` or sent as WhatsApp `visit_instructions` with a
  signed link `/care/<appointmentId>.<sig>` (`careToken`, first name only, 60 days). The board's "Checkout"
  column = completed without a checkout.
- Front desk fast lane (`DeskBar` above the calendar, `src/lib/front-desk/desk.ts`): search by mobile / name / file
  with today's visit → Check in, Walk-in (`walkIn`: book the tapped free time + check in in ONE transaction; a
  needed consent is still asked first), Book, Call, WhatsApp. One-tap contact = `ContactButtons`: `tel:` and
  `/whatsapp/open/<patientId>` (the clinic inbox chat, else wa.me on the device; inbox staff only).
- Help centre (`/help`, permission `help:view`, content `src/lib/help/guides.ts`): short step guides per role in Arabic
  and English. When a screen, tab or button name changes, update the guide (a test checks the links exist).
- Working hours: ONE place decides when a doctor works on a date (`src/lib/booking/hours.ts`): the weekly
  pattern (`staff_schedules`, several shifts per weekday, each at a branch; old rows with a break = two shifts)
  unless `schedule_exceptions` has a change for that date (off / special hours, which also adds extra days).
  Edits go through `src/lib/booking/working-hours.ts` (admin: all; reception: own branch; doctor: self if
  `doctors_edit_own_hours`). Never move or cancel bookings on an hours change: list the conflicts instead.

## Database changes

- Edit `src/db/schema.ts` → `pnpm db:generate` (Drizzle SQL) → `pnpm db:build-setup` regenerates
  `db/setup.sql` (schema + seed + RLS + roles in one transaction). A test fails if it is stale.
- Removing or renaming a table: add the old name to `RETIRED_TABLES` (`src/db/reset-sql.ts`). When a phase
  is released, copy its `db/setup.sql` into `tests/released-setup/` — a test runs today's `reset.sql` on each.
- The live demo database is updated automatically: the GitHub workflow "Update demo database" runs
  `db/reset.sql` + `db/setup.sql` as ONE transaction (`src/db/demo-update.ts`) whenever a merge to main
  changes either file (secrets: `SUPABASE_ADMIN_URL`, `APP_DB_PASSWORD`, `DEMO_STAFF_PASSWORD`). Both files
  must keep exactly one `begin;` and one `commit;` line. The SQL Editor paste still works as a fallback.
  Once real clinics exist, this reset must stop: use numbered `db/upgrades/NNNN_*.sql` files instead.
  `reset.sql` enforces this: it refuses (rolls back, changes nothing) when any patient is not fake or
  belongs to a non-demo clinic (`REAL_DATA_GUARD` in `src/db/reset-sql.ts`).
  Founder guide: `docs/DEPLOY.md` (Part G).
- If the tools can't be installed where you edit (no npm access), push the branch and run the GitHub
  workflow "Regenerate files" on it: it runs `db:generate`, `db:build-setup`, `docs:whatsapp` and
  Prettier, and commits the result back. Then run "Tests" on the branch.
- GitHub workflow "Tests" runs `pnpm check` on every pull request; merge only when it is green.
  When a phase is released, also update `latest` in `tests/demo-update.test.ts`.
- Supabase's `postgres` user is NOT a superuser. SQL we ship must work without superuser rights
  (e.g. never `ALTER ROLE ... NOBYPASSRLS`, never `DROP OWNED BY clinic_app`). Local databases are
  built by the non-superuser `local_admin` to catch this.
- Hosting: Vercel functions run in `bom1` (Mumbai, `vercel.json`) next to the database.
  Use Supabase's **transaction pooler** (port 6543) with user `clinic_app.<project-ref>`.
- Every change to records must call `audit()` (`src/lib/audit.ts`).

## Commands

- `pnpm db:local` — rebuild local database `derma_dev` from `db/setup.sql`
- `pnpm dev` — then open http://derma.localhost:3000
- `pnpm check` — lint, format, typecheck, tests (tests build a fresh `derma_test` DB from `db/setup.sql`;
  local Postgres must be running: `service postgresql start`)
- `pnpm e2e` — browser tests (Phase 0 roles + Phase 1 workflow) against a running `pnpm dev`;
  rebuild the demo database first with `pnpm db:local`
  (in the cloud workspace: `PW_CHROMIUM_PATH=/opt/pw-browsers/chromium pnpm e2e`)
